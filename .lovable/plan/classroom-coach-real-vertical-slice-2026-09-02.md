# Classroom Coach — Real Vertical Slice

Keep the current pages and visual design. Replace mocked behavior with a real backend, real AI calls, and persistent data.

## What changes for the user

- Sign in is required (email/password). Simulations, versions, rehearsals and reviews are saved to your account instead of the browser.
- Context documents are really uploaded, stored, text-extracted and chunked, with honest status: Uploading / Processing / Ready / Failed.
- "Build Scenario Draft" calls a real model server-side and returns a validated structured scenario specification. If it comes back malformed, one repair attempt is made, then an honest error with Retry — never fabricated content.
- Rehearsal turns are generated by the model, state persists per session, and every turn is logged as an event.
- Flags attach to the exact event and persist.
- After-Action Review is rebuilt from stored events; the reflective synthesis is an AI call over structured evidence, not the raw transcript.
- Admin-only screens: model/provider configuration and "Re-run this moment" plus mechanical assurance checks.
- Demo mode survives only as an explicit developer fallback toggle, off by default.

## Build order

1. **Backend + auth.** Enable Lovable Cloud. Auth (email/password), profiles, and a `user_roles` table with `has_role()` (admin/educator/learner). RLS on everything, owner-scoped.
2. **Database.** Tables: `profiles`, `user_roles`, `foundation_resources`, `people_profiles`, `context_documents`, `document_chunks`, `scenarios`, `scenario_versions`, `scenario_participants`, `rehearsal_sessions`, `simulation_states`, `simulation_events`, `flags`, `model_configurations`, `assurance_runs`. Normalized metadata columns plus a `spec jsonb` column for the frozen structured specification. Storage bucket `context-documents` (private, owner-scoped). `courses_or_groups` / `assignments` are created as minimal placeholder tables only — no UI this iteration.
3. **Foundation resources.** The five system resources seeded via migration into `foundation_resources` (id, name, version, body, active). Readable by any authenticated user, writable only by admins. Retrieved server-side at generation time; components stop hard-coding text.
4. **People Library.** The 10 seeded profiles migrate into `people_profiles` as persistent records. Scenario participants reference `profile_source_id` and hold only scenario-specific state — editing a scenario never mutates the persistent profile.
5. **Document ingestion.** Upload → storage → server-side extraction (TXT, DOCX via mammoth, PDF via a Worker-compatible parser) → chunk rows with document name, chunk index, dates, owning simulation. Retrieval starts as keyword/recency selection behind a `retrieveChunks()` interface; pgvector embeddings swap in behind the same interface if reliable.
6. **Structured scenario generation.** `generateStructuredScenario()` builds the prompt from foundation resources + People Library candidates + retrieved chunks + educator purpose, returns JSON validated with Zod against the specified schema, records provenance strings per derived element, and persists an editable draft spec.
7. **Publishing/versioning.** Publish freezes the spec into an immutable `scenario_versions` row with foundation version, context-document ids, creator, provider and model identifiers. Revisions always create a new version; sessions store the exact version id.
8. **Rehearsal.** `runSimulationTurn()` server-side, receiving only what the moment needs. Returns `{ visible_response, state_update }`, validated. Latent info, instructions and state never reach the client except through the instructor state drawer.
9. **State + events.** Every turn: load state → call model → validate update → persist new state → write a `simulation_events` row with prior state, action, response, update, resulting state, version and model identifiers.
10. **Flags.** Persistent, attached to `event_id`, with reason (including the two new reasons), optional note, status. Never alters the running simulation.
11. **After-Action Review.** Reconstructed from events; per-event inspector shows Before / Your action / What happened / What changed / Source & version / Flag status. `generateAfterActionReview()` produces Strengths Observed, Growth Opportunities, Possible Next Rehearsal — no scores, no "correct answer" language.
12. **Provider abstraction + assurance.** All four AI functions call one `modelAdapter` that reads the active `model_configurations` row (commercial API or OpenAI-compatible endpoint). Admin config screen at `/admin/models`. Admin "Re-run this moment" writes `assurance_runs`. Mechanical checks on the Assurance page: provenance present, published version exists, latent separated from visible, event has prior+resulting state, participant ids resolve, required output fields present.

## Technical notes

- AI runs through Lovable AI Gateway by default (`openai/gpt-5.6-sol` via the Responses API, streaming), wrapped by the adapter so a Penn State OpenAI-compatible endpoint can be selected later without UI changes. Credentials stay in server env; no keys in client code.
- All model calls are TanStack `createServerFn` handlers (`src/lib/ai/*.functions.ts`) with server-only helpers behind them; no Edge Functions in this stack.
- Zod schemas for the scenario specification and turn output live in a shared client-safe module so the Design Lab editor and the server validator agree.
- Protected pages move under `src/routes/_authenticated/`; public landing/auth stay top-level.
- localStorage store is replaced by server functions + TanStack Query; a one-time note tells existing users prototype data is not migrated.
